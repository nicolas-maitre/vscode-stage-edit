# Stage Edit

Makes **staged changes** editable from the Source Control diff view, the way **changes** already
are.

In VS Code, clicking a file under *Changes* gives you a diff whose right-hand side is the real
file on disk, so you can type straight into it. Clicking a file under *Staged Changes* gives you
a diff where both sides come from the built-in Git extension's `git:` filesystem provider, and
that provider is registered **read-only**. That is the whole reason you can look at your staged
copy but not touch it.

This extension serves the same index content under its own `stage-edit:` scheme and accepts
writes, turning a save into `git hash-object -w` + `git update-index`. Unstaged work in the same
file is never disturbed, which is the point: you can fix up what you are about to commit without
touching what you are not. By default the file on disk is kept in step with the
staged copy, and a save that would overwrite unstaged work stops and asks what to do — see
[how far the working tree follows](#how-far-the-working-tree-follows).

## How you get into it

Editing is **off by default** — the stock read-only diff is what opens, untouched.

- **Start typing** in a staged diff and you get asked whether to make it editable. (VS Code
  raises no event for an edit attempt on a read-only editor, so the keys that begin an edit are
  bound to a prompt command behind a context key that is only set while a read-only staged diff
  is focused. Everywhere else, those keys are not bound at all.)
- **Click the pencil** in the editor title bar, next to the tabs.
- **Right-click a staged file** in the Source Control view → *Open Editable Staged Changes*.
- Or run *Stage Edit: Open Editable Staged Changes* from the Command Palette.

The prompt offers four outcomes: this file for the rest of the session, this file permanently,
this project, or everywhere. Picking a scope writes the matching setting, so the next staged
diff you open skips the prompt and opens editable directly.

## Settings

| Setting | Default | What it does |
| --- | --- | --- |
| `stageEdit.editing.default` | `prompt` | `prompt`, `always`, or `never`. Put it in User settings for a global default, or in the workspace `.vscode/settings.json` for one project. |
| `stageEdit.editing.alwaysForPaths` | `[]` | Globs, relative to the repository root, that always open editable. This is the per-file scope. |
| `stageEdit.apply.mode` | `onSave` | `onSave` writes the index when you save. `live` writes it a moment after you stop typing. |
| `stageEdit.apply.liveDebounce` | `500` | Idle milliseconds before a live apply fires. |
| `stageEdit.apply.syncWorkingTree` | `askWhenDirty` | `askWhenDirty`, `whenSafe`, `never`, or `always`. See below. |
| `stageEdit.showEditorTitleButton` | `true` | Show the pencil in the editor title bar. |

`live` mode is implemented as a debounced `document.save()`, so both modes go through exactly
one write path and cannot drift apart.

### How far the working tree follows

| Value | On save, with unstaged changes in the file | Save succeeds? |
| --- | --- | --- |
| `askWhenDirty` *(default)* | Stops and asks: keep the file, overwrite it, or cancel | Unless you cancel |
| `whenSafe` | Leaves the file alone, stages the edit anyway | Always |
| `never` | Leaves the file alone (never writes it, ever) | Always |
| `always` | Overwrites them without asking | Always |

For a file with **no** unstaged changes all four behave the same, except `never`: the file on
disk follows the staged copy, so editing it does not conjure an unstaged diff out of nowhere.
The modes differ only in what happens when following along would cost you something.

`askWhenDirty` is the strict one and the only mode that can refuse a save. The staged copy and
the file on disk are kept in step, and when they cannot be, it stops rather than letting them
drift:

```
⌘S on foo.ts, which has unstaged changes
  → ⚠ foo.ts has unstaged changes.
     Applying this staged edit also writes foo.ts on disk,
     which would overwrite the unstaged changes in it.
     [ Only Update Index ]  [ Overwrite the File ]  [ Cancel ]
```

- **Only Update Index** stages the edit and leaves the file on disk untouched — the `whenSafe`
  outcome, for this one save. Nothing is lost.
- **Overwrite the File** stages the edit and writes the file, losing its unstaged changes. This
  puts the two back in step, so it will not ask again.
- **Cancel** means the save genuinely fails and your edit stays in the buffer. Nothing is
  written, *not even the index* — which is why the decision is made before `update-index` runs:
  a refused save must not be half-applied.

The non-destructive option comes first deliberately. Either of the first two choices applies to
that save only; to stop being asked, set the mode to `whenSafe` or `always`.

The file is written with `git checkout-index -f`, not by writing the blob bytes. That matters in
any repository with a clean/smudge filter: with `text eol=crlf`, the blob holds LF and the
checked-out file holds CRLF, so writing blob bytes would produce an LF file and an immediate
phantom diff. `checkout-index` applies the filters and the recorded file mode. Symlinks and
submodule entries are never written over, and because nothing on disk is at risk for those,
they never block a save either.

In `live` mode a dirty file is never interrupted with a dialog — a modal arriving a few hundred
milliseconds after a keystroke is no way to ask a question. The automatic apply holds back with
a note in the status bar, and the dialog waits until you save on purpose.

## What is covered

| Staged state | Editable |
| --- | --- |
| Modified (`M`) | yes — diffed against the HEAD blob |
| Added (`A`) | yes — opens as a single editor, since there is no HEAD side |
| Renamed (`R`) | yes — edits the index entry at the new path; git's rename pairing survives |
| Deleted (`D`) | no — there is no index entry to edit |
| Unmerged (`U`) | no — resolve the conflict first |
| Binary, submodule | no |

The cases that are not covered keep the stock read-only diff and say why in a notification.

## Details worth knowing

**Byte-exact round-trip.** Blobs are read with `cat-file` and written with a bare
`hash-object -w --stdin`, which applies no clean filters. Passing `--path` there would re-run
the clean filter over already-cleaned content and, in a repository that normalises line endings,
quietly rewrite every line. Saving a document you did not change produces the same object id.

**File modes are preserved.** The executable bit and symlink mode come from the existing index
entry and are written back unchanged.

**Outside changes.** If something else moves the index underneath an open editable document — a
`git add`, a commit, an unstage — the document is re-read, unless you have unsaved edits in it,
in which case your copy wins and is left alone.

**Self-healing.** If a file is enabled for editing but you somehow end up looking at the
read-only diff anyway, typing in it opens the editable view instead of asking again.

## Development

```bash
npm install
npm run watch       # esbuild, then F5 to launch the Extension Development Host
npm test            # 54 tests against real temporary repositories
npm run reinstall   # build, package, and install into your own VS Code
```

`npm run reinstall` is how you update an installed copy: a `.vsix` installed from disk never
auto-updates, so it has to be rebuilt and reinstalled. `--force` means the version number does
not need bumping. **Reload the window afterwards** (*Developer: Reload Window*) — VS Code keeps
running the already-loaded copy until you do.

For day-to-day work, prefer F5: the Extension Development Host loads straight from `dist/`, so
with `npm run watch` running you just reload that window. Nothing is installed, and it does not
disturb the copy in your real VS Code.

`scripts/gen-keybindings.mjs` regenerates the edit-intent keybindings in `package.json`; run
`npm run gen:keybindings` after changing the key list or the context key.
